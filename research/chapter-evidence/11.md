# Evidence sheet

## Question

How can an iOS app schedule device-owned reminders while keeping permission, persisted intent, system requests, payload validation, and re-entry routing separate?

## Public evidence

- Pushscheduler locked at `b047c4afb43b2a841505859c1d2cf3da11e0cc8e`.
- `MAAlertOrchestrator` requests/reads permission, persists a plan, replaces/refreshes/clears owned requests, and maintains a 32-request application cap.
- `MAScheduleVault` persists plan data and safely recovers from corrupt state.
- `MANotificationNavigator` validates a local scheme/payload and surfaces rather than auto-opens a route.
- Public README distinguishes device-owned local triggers from server/cross-device remote-push triggers.

## Approved generalized MemeArcade evidence

- Device-owned re-engagement can use a validated local plan and bounded notification projection.
- Re-entry is a native-owned route decision; remote/server events require a different push architecture.

No private text, plan, identifier, schedule, deep link, route, game reference, account state, source, payload, analytics, remote-push configuration, token, or server behavior is approved for publication.

## Planned diagram

Permission + validated device plan → durable vault → bounded local requests → notification tap → validated native route decision.
