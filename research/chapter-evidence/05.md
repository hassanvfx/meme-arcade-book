# Evidence sheet

## Question

How should a SwiftUI feature own, cancel, validate, and render asynchronous work without letting obsolete results override current user intent?

## Public evidence

- `receipe-app` locked at `51d090c26e1b1b7a89d82264938d06a4b047442b`.
- `RecipesViewModel` is `@MainActor` and publishes recipe, selection, loading, and failure state.
- `APIService` is an actor, accepts a session and mock mode, and maps decoding/server errors.
- The generic request path decodes a `Decodable & Sendable` response in a detached background task.
- `ImageCache` is an actor with a disk cache and detached background writes.
- Tests exercise mocked valid, empty, malformed, and cache cases.

## Approved generalized MemeArcade evidence

- Catalog/feed and product services use owned, cancellable asynchronous work.
- A result is validated before it becomes visible native product state.

No private service name, endpoint, request/response shape, payload, cache key, task graph, log, or metric is approved for publication.

## Planned diagram

Intent → feature-owned task → service actor → validated result/failure → main-actor product state.
