# Evidence sheet

## Question

How can an iOS feed keep remote WebView sessions responsive while bounding memory, network, reuse, and lifecycle risk?

## Public evidence

- GamePlayer locked at `2e9f314b8f775b2d9564950d1baeb2baa920421b`.
- Its pager tracks a current index and applies primary/inactive playback state to visible cells.
- Its stage cell lazy-loads only when primary and clears/cancels state on reuse.
- Its README states that UICollectionView reuse bounds player-cell count to the viewport and that preloading requires target-hardware profiling because adjacent pages increase `WKWebView` memory pressure.
- Its public journal records the explicit caveat that reused cells may reset in-progress web content.

## Approved generalized MemeArcade evidence

- Hybrid session activation and release must have explicit ownership.
- Prewarming is evaluated through target-device measurement, not assumed by default.

No private lifecycle trace, memory measurement, target, catalog, URL, source, session ID, analytics event, WebView configuration, or prewarm behavior is approved for publication.

## Claims requiring approval

- Any private performance comparison or memory/latency number.
- Any exact production WebView lifecycle or session-retention behavior.

## Planned diagram

Candidate → primary → active → leaving → reused/cleared, with metrics and rollback conditions around any adjacent-page prewarm experiment.
